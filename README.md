# RAG 기반 데이터시트 챗봇 (RAG ChatBot)

영문 하드웨어 데이터시트(PDF)를 분석해, 개발자가 질문했을 때 **한국어로 스펙과 출처 페이지를 함께 답변하는 RAG 기반 챗봇 프로젝트**입니다.  

---

## 1. 프로젝트 개요

- **진행 기간**: 2026.08 ~ 진행 중
- **프로젝트 형태**: 3인 팀 프로젝트
- **개발 배경 및 목적**
  - MCU, 센서, RTC 모듈 등의 영문 데이터시트는 분량이 길고 정보가 흩어져 있어 원하는 스펙을 빠르게 찾기 어렵습니다.
  - 일반적인 LLM만 사용할 경우 문서에 없는 정보를 생성하거나, 수치·단위를 잘못 답변할 가능성이 있습니다.
  - 이를 줄이기 위해 벡터 검색과 LLM을 결합한 RAG 구조를 바탕으로, **문서 근거 기반의 한국어 응답 시스템**을 구현하고자 시작했습니다.

## 2. 기술 스택

- **개발 언어**: Python
- **LLM**: Google Gemini API (`gemini-3.1-flash-lite`)
- **Validation / Schema**: Pydantic
- **Environment**: `python-dotenv`
- **Vector DB**: Chroma DB
- **문서 처리 / RAG 연동**: LangChain
- **Backend / UI 연동 대상**: FastAPI, Streamlit

---

## 3. 실행 방법

### 1) 실행 전 준비

- Python 3.10 이상 환경이 필요합니다.
- 가상환경 사용을 권장합니다.
- Google AI Studio에서 발급한 Gemini API Key가 필요합니다.

### 2) 환경 변수 설정

프로젝트 루트 경로에 `.env` 파일을 생성하고 API 키를 등록합니다.

```env
GEMINI_API_KEY=your_gemini_api_key_here
```

### 3) 의존성 설치

```bash
# uv 사용 시
uv pip install -r req.txt

# 일반 pip 사용 시
python -m pip install -r req.txt
```

### 4) 실행 방법

- **AI 엔진 단위 테스트**: `ai.py` 실행
- **전체 연동 테스트**: Streamlit 앱 또는 `app.py` 실행
- **RAG 연동 환경**: 데이터시트 청킹 및 벡터 검색 파이프라인 연결 후 통합 테스트 진행

### 5) 프론트엔드 실행 (`frontend/`)

로그인/회원가입/마이페이지, 데이터시트 업로드, 채팅 UI를 담당하는 React 프론트엔드입니다.
자세한 내용은 [`frontend/README.md`](frontend/README.md) 참고.

```bash
cd frontend
npm install
npm run dev
```

> ⚠️ 아직 팀 RAG 백엔드(FastAPI)가 없어서, 문서 분석/답변 로직은 프론트 내부 목업(`frontend/src/lib/embeddings.ts`, `llmClient.ts`)으로 동작합니다.
> `ai.py`의 Pydantic 응답 스키마(`answer`, `sources[].page`)에 맞춰 FastAPI 엔드포인트가 나오면 이 두 파일만 실제 API 호출로 교체하면 됩니다.
> 로그인/회원가입/마이페이지는 프론트에 포함된 자체 인증 서버(`frontend/server/`, Express + bcrypt + JWT)로 이미 동작합니다.

## 4. 시스템 아키텍처 및 핵심 포인트

### 시스템 아키텍처

```text
[사용자 질문]
      ↓
[UI / API 계층]
      ↓
[벡터 검색 (Chroma DB)]
      ↓
[관련 청크 추출]
      ↓
[LLM 응답 엔진]
      ↓
[Pydantic 기반 구조화 응답]
      ↓
[답변 + 출처 페이지 반환]
```

### 핵심 포인트

- **문서 근거 기반 응답**
  - 검색된 데이터시트 청크를 바탕으로만 답변하도록 설계
  - 문서 외 정보 생성 가능성을 줄이는 방향으로 프롬프트 구성

- **구조화 출력**
  - 답변과 출처를 일정한 JSON 형태로 반환
  - 후속 UI 및 API 계층에서 안정적으로 처리할 수 있도록 구성

- **출처 페이지 검증**
  - 검색 청크에 존재하는 페이지 번호만 응답에 포함되도록 검증
  - 응답 신뢰성을 높이기 위한 후처리 로직 적용

- **검색 결과 부재 시 예외 처리**
  - 관련 청크가 없을 경우 불필요한 LLM 호출 없이 즉시 안내 문구 반환
  - 비용과 오답 가능성을 줄이는 방향으로 설계

## 7. 개발 과정에서 고려한 점

### 1) 구조화 출력의 필요성
자유 형식 문자열만으로는 UI나 API 계층에서 답변과 출처를 안정적으로 분리해 사용하기 어렵습니다.  
그래서 응답을 Pydantic 기반 JSON 구조로 고정해 후속 모듈이 일관되게 처리할 수 있도록 구성했습니다.

### 2) 문서 외 정보 생성 방지
하드웨어 데이터시트는 숫자와 단위의 정확성이 중요하기 때문에,  
문서에 없는 정보를 임의로 보완하거나 일반 상식으로 추정해 답변하는 방식은 지양해야 한다고 판단했습니다.  
이에 따라 문서 근거 기반 응답과 출처 페이지 포함을 핵심 원칙으로 두고 개발하고 있습니다.

### 3) 병렬 개발을 위한 입출력 규격 정리
RAG, AI, UI를 나누어 동시에 개발해야 했기 때문에,  
청크 입력 형식과 응답 JSON 구조를 먼저 정리해 각 파트가 독립적으로 개발할 수 있도록 맞췄습니다.
